# 旧系统功能梳理

本文基于 `bak/` 中的旧代码、旧文档、API、服务层、页面入口和客户端目录梳理，目的是明确“重构前系统真正提供了哪些能力”，避免新重构偏离原系统定位。

## 系统定位

旧系统不是普通的 WireGuard 配置管理后台，而是一套完整的：

- WireGuard 配置建模系统
- Mesh 拓扑编排系统
- 服务端配置生成与应用系统
- MQTT 控制面系统
- 动态客户端注册与远程控制系统
- 配置同步状态跟踪系统

整体形态是 `FastAPI + Jinja2 + 原生 JS + SQLite + MQTT + Go Agent` 的运维控制平面。

## 核心组成

### 服务端

入口与结构：

- `bak/src/main.py`
- `bak/src/app/main.py`
- `bak/src/app/web/views.py`
- `bak/src/app/api/*.py`
- `bak/src/app/models/*.py`
- `bak/src/app/services/*.py`

服务端承担：

- 认证与会话
- 配置、节点、链路建模
- WireGuard 配置生成
- 服务端应用配置写盘
- 节点状态真相维护
- MQTT 下发与 ACK 消费
- enrollment token 与客户端引导
- 系统状态、备份恢复

### Web 前端

旧前端不是 SPA，而是：

- `bak/front/templates/*.html`
- `bak/front/static/js/*.js`
- `bak/front/static/css/*.css`

特点：

- 页面由 FastAPI/Jinja2 渲染
- 局部逻辑通过原生 JS 驱动
- 大量业务逻辑依赖服务端 API 返回结果
- 页面之间围绕“配置详情 / Mesh / 应用 / 端点控制”形成闭环

### Go 客户端

客户端是系统主能力之一，不是附属工具：

- `bak/client/cmd/*`
- `bak/client/agent/*`
- `bak/client/config/*`
- `bak/client/mqtt/*`
- `bak/client/wireguard/*`

客户端承担：

- 导入 `.wgm` 注册文件
- enrollment
- 保存身份与 profile
- MQTT 收发与串行执行
- 本地 WireGuard 配置写入
- 启停隧道
- ACK 与状态上报

## 旧系统关键数据模型

基于 `bak/src/app/models/DATABASE_SCHEMA.md`，核心表包括：

- `auth`
- `wireguard_configs`
- `nodes`
- `tags`
- `node_tags`
- `node_peer_links`
- `system_settings`
- `endpoint_runtime_status`
- `endpoint_control_logs`
- `node_config_state`
- `client_enrollment_tokens`

其中最关键的不是 CRUD 表，而是两张状态真相表：

- `endpoint_runtime_status`
- `node_config_state`

这两张表支撑了：

- 在线态
- 控制 ACK
- 配置同步态
- 本地上报态
- 服务端应用态

## 页面入口梳理

旧页面入口位于 `bak/src/app/web/views.py`：

- `/`
- `/setup`
- `/login`
- `/settings`
- `/config/{config_name}`
- `/config/{config_name}/mesh`
- `/config/{config_name}/apply`
- `/config/{config_name}/endpoint`

这意味着旧系统的主工作流是：

1. 初始化 / 登录
2. 配置详情
3. Mesh 链路
4. 配置应用
5. 端点控制

## 结论

旧系统的本质是一套“服务端主导、客户端协同、MQTT 闭环驱动”的 WireGuard 运维控制平面。

新重构必须至少恢复以下主线能力，才能算“重构旧系统”而不是“重写一个新后台”：

- 配置 / 节点 / Mesh 三层建模
- WireGuard 配置生成与服务端应用
- 状态机：`desired/staged/confirmed/reported`
- 动态节点 MQTT 控制闭环
- enrollment / `.wgm` / bootstrap
- 端点控制与 ACK 日志
- 备份恢复
