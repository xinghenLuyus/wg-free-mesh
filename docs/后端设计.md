# 后端设计

## 目标

后端负责承载本项目的业务真相，前端负责表达、操作和反馈。

本项目的本质目标是帮助用户生成、调整、保存和下发 WireGuard 配置文档，因此后端设计必须围绕“配置生成”展开。

## 核心职责

- 用户认证与会话管理
- 配置管理
- 节点管理
- Peer Link / Mesh 规则管理
- WireGuard 配置生成
- 配置三态管理
- 端点运行态与控制日志
- WebSocket 实时事件
- MQTT 公网引导参数管理
- 备份恢复
- 系统状态聚合

## 配置三态模型

配置存在三个形态，后端必须明确区分。

### 系统态

- 指用户在系统页面中通过配置、节点、链路等操作得到的系统生成配置
- 这是系统根据当前业务数据自动计算出的结果
- 它反映的是当前业务模型推导出来的标准配置文本

### 同步态

- 指系统准备同步和下发的配置文本
- 系统态原则上应自动同步到同步态
- 用户可以手动编辑同步态
- 用户可以关闭自动同步
- 增加同步态的目的，是给用户保留手动调整配置文件的空间

### 下发态

- 指同步态最终下发到客户端的配置
- 同步态原则上应自动下发到下发态
- 客户端暂缓时，后端先保留下发所需字段和状态位

## 后端状态原则

- 系统态来自业务数据计算
- 同步态允许人工覆盖
- 下发态代表实际投递结果
- 页面必须能明确看出三态之间是否一致
- 不能把同步态和系统态混成一个字段

## 分层

### API 层

路径：`src/app/api/v1/`

职责：

- 绑定请求
- 返回响应
- 暴露 WebSocket
- 只做轻量协调

### Service 层

路径：`src/app/services/`

职责：

- 编排用例
- 发布实时事件
- 调度配置刷新、同步、端点控制

### Repository 层

路径：`src/app/repositories/`

职责：

- 持久化访问
- 配置预览生成
- 三态状态保存
- 备份文件管理

### Infrastructure 层

路径：`src/app/infrastructure/`

职责：

- SQLite 连接
- 配置文件目录
- 备份目录
- 后续 MQTT / 执行器接入点

## 重要接口分组

- `/api/v1/auth`
- `/api/v1/configs`
- `/api/v1/configs/{config_id}/nodes`
- `/api/v1/configs/{config_id}/peer-links`
- `/api/v1/configs/{config_id}/mesh`
- `/api/v1/configs/{config_id}/sync-status`
- `/api/v1/configs/{config_id}/endpoint`
- `/api/v1/settings`
- `/api/v1/backups`
- `/api/v1/system`
- `/api/v1/ws/events`

## 实时性策略

强实时内容优先使用 WebSocket：

- 节点运行快照
- 控制日志
- 配置同步状态
- 系统状态聚合

首屏仍先走 REST，随后由 WebSocket 增量更新。
