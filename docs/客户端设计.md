# wfm 客户端设计

## 目标

`client/` 负责承载 `wfm` 动态节点的本地运行能力。

客户端不做主页面，不做桌面控制台，不做浏览器式交互。客户端唯一目标是：

- 安装后无感知常驻运行
- 通过 `wfmctl` 完成本地绑定与维护
- 接收服务端通过 MQTT 下发的配置与控制命令
- 管理本地 WireGuard 生命周期
- 稳定上报本地真实运行状态

## 形态

客户端只保留两类程序：

### `wfm-agent`

- 后台核心进程
- 负责 profile 管理、MQTT 连接、WireGuard 应用、状态采集、状态上报
- 三个平台都运行同一套共享核心
- 不直接暴露图形界面

### `wfmctl`

- 本地命令行控制器
- 通过本地 IPC 调用 `wfm-agent`
- 用于绑定 profile、查看状态、启动停止、删除 profile、读取日志

可选附加项：

- Windows 托盘程序可以后续补充，但不是主路径，也不参与核心架构判断

## 设计原则

- 客户端没有主要页面
- 所有交互优先走命令行
- 后台运行模型优先考虑系统服务能力，而不是应用自启动技巧
- MQTT 必须一步到位，不再先做一个会导致后续返工的弱版本
- `wfm-agent` 负责业务真相，`wfmctl` 只负责本地控制
- 本地 profile 必须彼此隔离，不能再走单实例全局配置模型
- HTTP 只用于首次绑定；运行期所有业务通信都走 MQTT

## 安装与启动模型

### Windows

- 安装产物：
  - `wfm-agent.exe`
  - `wfmctl.exe`
- 安装方式：
  - 安装包把 `wfm-agent` 注册为 Windows Service
- 启动方式：
  - 服务安装完成后自动启动
  - 开机由 Service Control Manager 拉起
- 运行要求：
  - 不依赖用户登录
  - 不依赖启动目录快捷方式
  - 不依赖计划任务模拟常驻

建议服务名：

- `WFMService`

### Linux

- 安装产物：
  - `wfm-agent`
  - `wfmctl`
- 安装方式：
  - 安装 `systemd` unit
- 启动方式：
  - `systemctl enable --now wfm-agent.service`
- 运行要求：
  - 开机自动启动
  - 崩溃自动重启
  - 日志统一进入 `journal`

建议 unit：

- `wfm-agent.service`

建议策略：

- `Restart=on-failure`
- `RestartSec=3`
- 后续再视需要补 `Type=notify`

### macOS

- 安装产物：
  - `wfm-agent`
  - `wfmctl`
- 安装方式：
  - 安装 `LaunchDaemon`
- 启动方式：
  - 由 `launchd` 常驻管理
- 运行要求：
  - 不依赖用户登录
  - 不依赖 Login Item
  - 不使用 GUI App 常驻

建议 label：

- `io.wfm.agent`

## 绑定模型

客户端不再导入注册文件，不再走 enrollment 文件模型，不再维护节点公私钥身份体系。

安装完成后，管理员直接在本机执行：

```powershell
wfmctl bind --server https://example.com --token <5分钟临时token>
```

或等价命令：

```powershell
wfmctl bind https://example.com <token>
```

绑定流程：

1. 服务端为某个动态节点签发 5 分钟有效的临时绑定 token
2. 管理员在目标设备运行 `wfmctl bind`
3. `wfmctl` 通过 HTTPS 调用服务端绑定接口
4. 服务端返回：
   - profile 基本信息
   - MQTT 连接参数
   - MQTT topic 范围
   - 初始同步态配置
5. 客户端写入本地 profile，并启动该 profile worker

## 本地 profile 模型

一个 profile 表示：

- 当前设备
- 绑定到某个服务端
- 某个配置下
- 某个动态节点

客户端必须支持多 profile 并行。

### 推荐目录结构

```text
client-data/
  profiles/
    <profile_id>/
      profile.json
      binding.json
      runtime.json
      desired.conf
      applied.conf
```

### 文件职责

#### `profile.json`

静态元数据：

- `profile_id`
- `server_url`
- `config_id`
- `config_name`
- `node_id`
- `node_name`
- `platform`
- `tunnel_name`
- `created_at`
- `updated_at`

#### `binding.json`

绑定时服务端返回的初始配置：

- `mqtt`
- `topics`
- `bound_at`
- `client_version`

#### `runtime.json`

本地运行时状态快照：

- `agent_state`
- `mqtt_state`
- `wireguard_state`
- `config_version`
- `last_seen_at`
- `last_applied_at`
- `last_error`
- `boot_id`
- `session_id`

#### `desired.conf`

- 最新一期服务端下发的目标配置

#### `applied.conf`

- 最后一次实际应用到本地 WireGuard 的配置

## 客户端进程模型

### `wfm-agent`

内部建议拆成：

- `profile manager`
  - 扫描、加载、卸载本地 profile
- `profile worker`
  - 每个 profile 一个独立 worker
- `mqtt session`
  - 每个 profile 一个独立 MQTT 会话
- `wireguard manager`
  - 每个 profile 一个本地隧道控制器
- `status reporter`
  - 统一节奏上报状态

### `wfmctl`

只做本地控制，不直接触碰远端业务：

- `bind --server --token`
- `list`
- `status [profile]`
- `start <profile>`
- `stop <profile>`
- `restart <profile>`
- `remove <profile>`
- `logs [profile]`

## MQTT 设计

MQTT 不再把“连接上线”误当成“客户端真实在线”。

当前推荐集成方式：

- Broker 继续使用 EMQX
- `wfm` 服务端是 MQTT 账号与权限的真相源
- EMQX 负责连接接入、协议处理和消息路由
- `wfm` 负责节点专属凭据签发与授权判断

客户端真实状态至少拆成四层：

- `agent_state`
  - agent 是否存活
- `mqtt_state`
  - broker 连接是否健康
- `wireguard_state`
  - 本地隧道是否运行
- `config_state`
  - 最新配置是否成功应用

### 连接原则

- 每个 profile 固定一个稳定 `client_id`
- 每个 profile 独立会话
- 每个节点独立一套 MQTT 凭据
- 每个 profile 独立 topic
- 不允许多个 profile 共享一条全局 MQTT 状态
- 所有运行期通信都走 `MQTT over TLS`
- Broker ACL 必须按 `config_id + node_id` 收口，任何节点只能访问自己的 topic

推荐拆分：

- **AuthN**：EMQX 内建账号库
- **AuthZ**：EMQX HTTP Authorization 回查 `wfm`
- **账号真相源**：`wfm`
- **ACL 真相源**：`wfm`

绑定时：

- `wfm` 生成或轮换节点专属 MQTT 用户名/密码
- `wfm` 通过 EMQX 管理 API 创建或更新该节点账号
- 客户端只接收当前节点唯一可用的 MQTT 凭据

隔离要求：

- `c1` 只能读写 `c1` 自己的 topic
- `c2` 只能读写 `c2` 自己的 topic
- 单节点被入侵后，不允许横向伪造其它节点的 ACK、状态和配置事件

### topic 建议

下行：

- `wfm/{config_id}/{node_id}/config/push`
- `wfm/{config_id}/{node_id}/control`

上行：

- `wfm/{config_id}/{node_id}/status`
- `wfm/{config_id}/{node_id}/control/ack`
- `wfm/{config_id}/{node_id}/config/ack`
- `wfm/{config_id}/{node_id}/event`

说明：

- topic 规则固定按 `config_id + node_id` 展开
- 客户端不允许访问通配型共享 topic
- Broker 不允许通过单个账号覆盖多个节点

### presence 设计

presence 不只靠 MQTT connect/disconnect 判断。

建议同时使用：

- retained 状态消息
- LWT 离线消息
- `last_seen_at`
- `boot_id`
- `session_id`
- 周期心跳

这样服务端才能区分：

- 进程刚启动但配置未应用
- MQTT 已连但 WireGuard 未运行
- WireGuard 正常但控制面断线
- 客户端异常退出
- 客户端正常停机

### 状态上报建议字段

每次状态上报至少包含：

- `profile_id`
- `config_id`
- `node_id`
- `boot_id`
- `session_id`
- `agent_state`
- `mqtt_state`
- `wireguard_state`
- `config_version`
- `desired_sha256`
- `applied_sha256`
- `last_error`
- `reported_at`

### ACK 设计

配置下发和控制命令都必须有 ACK。

约束：

- 服务端向客户端下发配置，不以“已发布到 broker”视为成功
- 服务端向客户端下发控制命令，不以“已发布到 broker”视为成功
- 只有客户端返回对应 ACK，且 ACK 状态为成功，才算这次动作真正完成

也就是说，以下两类消息都必须一来一回闭环：

- 配置下发
- 控制命令

控制命令 ACK 至少三态：

- `accepted`
- `applied`
- `failed`

必要时再加：

- `skipped`
- `superseded`

同一 profile 内的控制命令必须串行执行，避免：

- 配置下发和 stop/restart 并发
- 多次 sync 覆盖顺序混乱

### 不需要 ACK 的消息

以下消息不做 ACK：

- 客户端主动状态上报
- 客户端事件日志回显

这两类消息属于客户端到服务端的单向推送：

- 客户端发出后即可视为完成
- 服务端负责存储、展示和超时清理
- 不再反向回一个“收到状态”或“收到日志”的 ACK

## 最小服务端 API

为了让 `wfm-agent` 能独立完成工作，服务端至少要补这几类客户端专用接口。

注意：绑定接口使用客户端专用临时 token，不复用后台管理员 token。

### 1. 绑定

#### `POST /api/client/v1/bind`

用途：

- 用 5 分钟临时 token 完成客户端绑定

请求：

- `token`
- `hostname`
- `platform`
- `client_version`

响应：

- `profile`
- `mqtt`
- `topics`
- `desired_conf`

说明：

- 这是运行期唯一允许使用的 HTTP 初始化接口
- 绑定成功后，客户端不再依赖 HTTP 参与业务主链
- 服务端在绑定时负责生成或轮换节点专属 MQTT 凭据，并同步到 EMQX

### 2. EMQX 授权回查

#### `POST /api/internal/emqx/authz`

用途：

- 供 EMQX 在客户端 publish / subscribe 时回查授权结果

请求核心字段：

- `username`
- `clientid`
- `topic`
- `action`

响应语义：

- `allow`
- `deny`

说明：

- `wfm` 不再把 ACL 静态复制到多处，而是始终以当前节点业务状态为真相源
- 节点停用、删除、配置停用后，授权结果必须即时反映

## 第一阶段实现边界

第一阶段只做：

- `wfm-agent`
- `wfmctl`
- 多 profile 本地模型
- bind token 绑定
- EMQX 节点专属账号下发
- EMQX HTTP AuthZ 回查
- MQTT 下发配置和控制
- 配置 ACK 与控制 ACK
- WireGuard 本地管理
- 状态与单向事件上报
- Windows/Linux/macOS 服务安装模型

第一阶段不做：

- 主页面
- 桌面控制台
- 跨平台托盘统一实现
- 自动升级
- 复杂安装器 UI
- 注册文件
- enrollment 体系
- 节点公私钥身份体系

## 目录建议

建议 `client/` 最终目录：

```text
client/
  cmd/
    agent/
    ctl/
  agent/
  config/
  profiles/
  ipc/
  mqtt/
  wireguard/
  localstate/
  platforms/
    windows/
    linux/
    darwin/
```

说明：

- `tray/` 不进入第一阶段主路径
- `ipc/` 只服务 `wfmctl -> wfm-agent`
- `platforms/` 只放安装、服务管理和平台命令包装

## 当前结论

客户端应该按“无界面后台系统组件”来设计，而不是按“桌面应用”来设计。

`wfm-agent` 是唯一核心，`wfmctl` 是唯一主交互入口。  
绑定只走一次 HTTPS 临时 token，后续业务通信全部走 MQTT。  
托盘未来可以加，但永远只是附加项，不是主路径。
