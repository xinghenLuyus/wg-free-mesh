# wfm 客户端设计

## 目标

`client/` 负责承载 `wfm` 动态节点的本地运行能力。

客户端不做主页面，不做桌面控制台，不做浏览器式交互。客户端唯一目标是：

- 安装后无感知常驻运行
- 通过 `wfmctl` 完成本地绑定与维护
- 接收服务端通过 MQTT 下发的配置与控制命令
- 管理本地 WireGuard / AmneziaWG 隧道生命周期
- 稳定上报本地真实运行状态

## 形态

客户端只保留两类程序：

### `wfm-agent`

- 后台核心进程
- 负责 profile 管理、MQTT 连接、隧道配置应用、状态采集、状态上报
- 三个平台都运行同一套共享核心
- 不直接暴露图形界面

### `wfmctl`

- 本地命令行控制器
- 用于绑定 profile、查看本机绑定状态、安装和维护系统级 `wfm-agent` 服务
- 不通过本地 IPC 控制单个 profile
- 不直接执行 WireGuard 控制动作

可选附加项：

- Windows 托盘程序可以作为附加能力独立补充，但不是主路径，也不参与核心架构判断

生产节点必须将 `wfm-agent` 安装为系统级服务运行。远程控制面板不负责提权，也不绕过本机权限；`wg` / `awg` 诊断、WireGuard / AmneziaWG 启停、配置应用等能力依赖客户端在本机持有足够权限。`wfmctl` 只做本机绑定与服务生命周期管理。

统一 CLI：

```text
wfmctl install
wfmctl uninstall
wfmctl uninstall --purge
wfmctl bind --server <url> --token <token>
wfmctl bind <url> <token>
wfmctl unbind <profile_id>
wfmctl unbind --all
wfmctl list
wfmctl status
wfmctl logs
wfmctl logs --lines <n>
wfmctl start
wfmctl stop
wfmctl restart
wfmctl version
wfmctl --version
wfmctl -v
wfmctl help [command]
```

命令语义：

- `wfmctl install`：安装系统服务、设置开机自启、立即启动服务，并把当前 `wfmctl` 所在目录加入全局命令路径。安装成功后输出客户端终端标识，并执行 `wg -v`、`awg -v` 做 WireGuard / AmneziaWG 工具链检查；检查仅提示缺失或异常，不改变安装成功状态。
- `wfmctl uninstall`：停止服务、取消开机自启、删除服务定义，并移除 `install` 添加的全局命令路径；默认保留本机 profile、runtime 和日志。
- `wfmctl uninstall --purge`：在 `uninstall` 基础上彻底删除本机 profile、runtime 和日志目录。
- `wfmctl bind`：使用服务端生成的一次性 token 写入本机 profile。
- `wfmctl unbind <profile_id>`：移除本机某个绑定，删除该 profile 的本地凭据、目标配置和运行文件；如果服务正在运行，需要重启整个 `wfm-agent` 服务使移除立即生效。
- `wfmctl unbind --all`：移除本机全部绑定；这是高风险操作，必须显式传入 `--all`。
- `wfmctl list`：列出本机已绑定 profile。
- `wfmctl status`：展示本机服务状态、profile 数量和 profile 文件完整性。
- `wfmctl logs`：查看系统服务日志。
- `wfmctl start`：启动已安装的系统服务，不创建或修改服务定义。
- `wfmctl stop`：停止系统服务，保留服务定义、开机自启配置、profile 和日志。
- `wfmctl restart`：重启系统服务，让 agent 重新扫描本机 profile。
- `wfmctl version`：显示客户端版本。
- `wfmctl --version` / `wfmctl -v`：显示客户端版本，等价于 `wfmctl version`。

`unbind` 只表示移除本机绑定文件，不等同于服务端撤销节点权限。服务端侧权限回收仍由控制台“重置客户端”、节点转静态、节点删除或配置停用触发。

不提供本地 profile 级 `start/stop/restart`。客户端本机只维护系统服务，具体配置下发、WireGuard 启停、诊断信息读取和探测都由服务端通过 MQTT 向 `wfm-agent` 发出。

旧版 `wfmctl service ...` 子命令不再作为用户入口。用户只感知 `wfmctl`，`wfm-agent` 是后台实现细节。

## 设计原则

- 客户端没有主要页面
- 所有交互优先走命令行
- 后台运行模型优先考虑系统服务能力，而不是应用自启动技巧
- MQTT 必须一步到位，不再先做一个会导致后续返工的弱版本
- `wfm-agent` 负责运行期通信和本机执行，`wfmctl` 只负责本机绑定与系统服务维护
- 本地 profile 必须彼此隔离，不能再走单实例全局配置模型
- HTTP 只用于首次绑定；运行期所有业务通信都走 MQTT
- 不做本地 IPC，不做本地 profile 级控制命令
- 本地用户不能绕过服务端直接控制某个 profile 的 WireGuard 生命周期
- 移除绑定是本地文件维护动作；没有 IPC 的最终形态下，移除后通过重启整个系统服务使运行态收敛
- 用户命令不暴露 `service` 层级，不要求用户理解 `wfm-agent`
- `install` 必须让 `wfmctl` 全局可用；如果用户移动了二进制目录，重新执行当前位置的 `wfmctl install` 修复路径

## 安装与启动模型

### Windows

- 安装产物：
  - `wfm-agent.exe`
  - `wfmctl.exe`
- 安装方式：
  - 安装包把 `wfm-agent` 注册为 Windows Service
  - 把 `wfmctl.exe` 所在目录写入 Machine PATH
- 启动方式：
  - `wfmctl install` 完成注册、设置开机自启并自动启动
  - `wfmctl start` 仅启动已安装服务
  - 开机由 Service Control Manager 拉起
- 运行要求：
  - 不依赖用户登录
  - 不依赖启动目录快捷方式
  - 不依赖计划任务模拟常驻

建议服务名：

- `WfmAgent`

服务显示名：

- `WG Free Mesh Agent`

服务账号：

- `LocalSystem`

机器级目录：

- `C:\ProgramData\wg-free-mesh\profiles`
- `C:\ProgramData\wg-free-mesh\runtime`
- `C:\ProgramData\wg-free-mesh\logs`

### Linux

- 安装产物：
  - `wfm-agent`
  - `wfmctl`
- 安装方式：
  - 安装 `systemd` unit
  - 创建指向当前二进制的全局命令入口，确保 `wfmctl` 可直接执行
- 启动方式：
  - `wfmctl install` 写入 unit、执行 `systemctl enable` 并启动服务
  - `wfmctl start` 仅执行 `systemctl start wfm-agent.service`
- 运行要求：
  - 开机自动启动
  - 崩溃自动重启
  - 日志统一进入 `journal`

建议 unit：

- `wfm-agent.service`

建议策略：

- `Restart=on-failure`
- `RestartSec=3`
- 后续再视需要补 `Type=notify`

第一阶段运行账号：

- `root`

机器级目录：

- `/etc/wg-free-mesh/profiles`
- `/var/lib/wg-free-mesh/runtime`
- `/var/log/wg-free-mesh`

后续可降权为专用用户，并按发行版能力支持情况配置 `CAP_NET_ADMIN`、`CAP_NET_RAW`。

### macOS

- 安装产物：
  - `wfm-agent`
  - `wfmctl`
- 安装方式：
  - 安装 `LaunchDaemon`
  - 创建指向当前二进制的全局命令入口，确保 `wfmctl` 可直接执行
- 启动方式：
  - `wfmctl install` 写入 plist、注册 LaunchDaemon 并启动服务
  - `wfmctl start` 在 plist 已存在时重新 bootstrap 或 kickstart 服务
  - `wfmctl stop` 通过 `launchctl bootout` 停止当前系统域 job
  - 由 `launchd` 常驻管理
- 运行要求：
  - 不依赖用户登录
  - 不依赖 Login Item
  - 不使用 GUI App 常驻

建议 label：

- `mesh.wg-free.wfm-agent`

运行账号：

- `root`

机器级目录：

- `/Library/Application Support/WG Free Mesh/profiles`
- `/Library/Application Support/WG Free Mesh/runtime`
- `/Library/Logs/wg-free-mesh`

## 本地构建命令

正式发布构建在 `client/` 目录执行：

```powershell
cd D:\wenjian\stepsave\project\wg-free-mesh\client
python build_release.py
```

发布构建读取 [src/pyproject.toml](D:/wenjian/stepsave/project/wg-free-mesh/src/pyproject.toml) 的 `[project].version`，通过 Go `ldflags` 注入 `wfmctl` / `wfm-agent`，并输出 `client/dist/wfm-client-<goos>-<goarch>-v<version>.zip`。

只构建单个平台：

```powershell
python build_release.py --target windows/amd64
```

开发期手动 `go build` 只用于调试，版本显示为 `dev`，不作为正式发布产物：

```powershell
go build ./...
go run ./cmd/ctl version
go run ./cmd/agent
```

项目唯一版本源是 `src/pyproject.toml` 的 `[project].version`。客户端源码里的 `Version = "dev"` 只是未注入版本时的开发占位。

安装完成后，管理员直接在本机执行统一绑定命令：

```powershell
wfmctl bind --server https://example.com --token <5分钟临时token>
```

或等价命令：

```powershell
wfmctl bind https://example.com <token>
```

绑定流程：

1. 服务端为某个动态节点签发 5 分钟有效的临时绑定 token
2. 管理员在目标设备运行 `wfmctl bind`
3. `wfmctl` 通过 HTTPS 调用服务端绑定接口
4. 服务端返回：
   - profile 基本信息
   - MQTT 连接参数
   - MQTT topic 范围
   - 初始同步态配置
5. 客户端写入本地 profile，并启动该 profile worker

约束补充：

- 绑定命令必须是一次性命令，5 分钟过期且只能成功使用一次。
- 服务端生成的命令形态以 `wfmctl bind --server ... --token ...` 为准，前端只负责展示和复制。
- `bind` 响应不携带也不保存配置所属隧道协议。协议由服务端在每次 MQTT `config/push`、`control`、`detect`、`info` payload 中下发，客户端按当次 payload 选择工具链。Linux/macOS 启停隧道使用 `wg-quick` / `awg-quick`，Windows 启停隧道使用 `wireguard.exe` / `amneziawg.exe` 的 tunnel service 命令；状态检查使用 `wg` / `awg`。
- 静态节点不能生成绑定命令。
- 动态节点转为静态节点后，服务端必须回收该节点 MQTT 凭据和客户端绑定权限。
- 控制台允许“重置客户端”，重置后该节点回到未初始化状态，原有 MQTT 权限和运行态同时清空。

## 本地 profile 模型

一个 profile 表示：

- 当前设备
- 绑定到某个服务端
- 某个配置下
- 某个动态节点

客户端必须支持多 profile 并行。

### 推荐目录结构

```text
client-data/
  profiles/
    <profile_id>/
      profile.json
      binding.json
      runtime.json
      desired.conf
      applied.conf
```

### 文件职责

#### `profile.json`

静态元数据：

- `profile_id`
- `server_url`
- `config_id`
- `config_name`
- `node_id`
- `node_name`
- `interface_name`
- `platform`
- `tunnel_name`
- `created_at`
- `updated_at`

#### `binding.json`

绑定时服务端返回的初始配置：

- `mqtt`
- `topics`
- `bound_at`
- `client_version`

#### `runtime.json`

本地运行时状态快照：

- `agent_state`
- `mqtt_state`
- `wireguard_state`
- `config_version`
- `last_seen_at`
- `last_applied_at`
- `last_error`
- `boot_id`
- `session_id`

#### `desired.conf`

- 最新一期服务端下发的目标配置

#### `applied.conf`

- 最后一次实际应用到本地 WireGuard 的配置

## 客户端进程模型

### `wfm-agent`

内部建议拆成：

- `profile manager`
  - 扫描、加载、卸载本地 profile
- `profile worker`
  - 每个 profile 一个独立 worker
- `mqtt session`
  - 每个 profile 一个独立 MQTT 会话
- `tunnel manager`
  - 每个 profile 一个本地隧道控制器
- `status reporter`
  - 统一节奏上报状态

### `wfmctl`

只做本机绑定和系统服务维护，不直接触碰远端业务：

- `install`
- `uninstall`
- `uninstall --purge`
- `bind --server --token`
- `unbind <profile_id>`
- `unbind --all`
- `list`
- `status`
- `logs`
- `start`
- `stop`
- `restart`
- `version`
- `help [command]`

`wfmctl unbind` 是本机绑定文件维护命令，不是 profile 级运行控制命令。它删除本机保存的 profile、MQTT 凭据、目标配置和运行文件；如果服务正在运行，命令需要重启整个 `wfm-agent` 服务，避免已加载的 MQTT session 继续使用内存中的旧凭据。

`wfmctl` 不提供 profile 级启动、停止、重启和日志命令。多个 profile 由同一个系统级 `wfm-agent` 一起加载、一起运行、一起停止。服务端是具体控制动作的唯一入口，本地命令不绕过服务端直接操作 WireGuard。

## MQTT 设计

MQTT 不再把“连接上线”误当成“客户端真实在线”。

当前推荐集成方式：

- Broker 继续使用 EMQX
- `wfm` 服务端是 MQTT 账号与权限的真相源
- EMQX 负责连接接入、协议处理和消息路由
- `wfm` 负责节点专属凭据签发与授权判断

客户端对控制台只暴露三种最终状态：

- `在线`
- `掉线`
- `离线`

内部实现仍可维护更细的 `agent_state`、`mqtt_state`、`wireguard_state`，但投影到控制台时统一收束成以上三态。

### 连接原则

- 每个 profile 固定一个稳定 `client_id`
- 每个 profile 独立会话
- 每个节点独立一套 MQTT 凭据
- 每个 profile 独立 topic
- 不允许多个 profile 共享一条全局 MQTT 状态
- 所有运行期通信都走 `MQTT over TLS`
- Broker ACL 必须按 `config_id + node_id` 收口，任何节点只能访问自己的 topic

推荐拆分：

- **AuthN**：EMQX 内建账号库
- **AuthZ**：EMQX HTTP Authorization 回查 `wfm`
- **账号真相源**：`wfm`
- **ACL 真相源**：`wfm`

绑定时：

- `wfm` 生成或轮换节点专属 MQTT 用户名/密码
- `wfm` 通过 EMQX 管理 API 创建或更新该节点账号
- 客户端只接收当前节点唯一可用的 MQTT 凭据

隔离要求：

- `c1` 只能读写 `c1` 自己的 topic
- `c2` 只能读写 `c2` 自己的 topic
- 单节点被入侵后，不允许横向伪造其它节点的 ACK、状态和配置事件

### topic 建议

下行：

- `wfm/{config_id}/{node_id}/config/push`
- `wfm/{config_id}/{node_id}/control`
- `wfm/{config_id}/{node_id}/detect`
- `wfm/{config_id}/{node_id}/info`

上行：

- `wfm/{config_id}/{node_id}/config/push/ack`
- `wfm/{config_id}/{node_id}/control/ack`
- `wfm/{config_id}/{node_id}/detect/ack`
- `wfm/{config_id}/{node_id}/info/ack`
- `wfm/{config_id}/{node_id}/event`
- `wfm/{config_id}/{node_id}/heartbeat`

说明：

- topic 规则固定按 `config_id + node_id` 展开
- 客户端不允许访问通配型共享 topic
- Broker 不允许通过单个账号覆盖多个节点
- ACK 只反馈命令执行状态；命令行输出统一通过 `event` 上报
- `info` 当前用于用户主动触发裸 `wg` 或 `awg` 诊断，客户端按 payload 中的 `tunnel_protocol` 返回对应工具输出

### presence 设计

presence 不只靠 MQTT connect/disconnect 判断。

建议同时使用：

- retained 状态消息
- LWT 离线消息
- `last_seen_at`
- `boot_id`
- `session_id`
- 周期心跳

这样服务端才能区分：

- 进程刚启动但配置未应用
- MQTT 已连但 WireGuard 未运行
- WireGuard 正常但控制面断线
- 客户端异常退出
- 客户端正常停机

控制台最终态收束规则：

- 首次未绑定或已重置：`离线`
- 收到遗言：`离线`
- 节点转静态、节点停用、绑定权限被删除：`离线`
- 所有有效可达信号都超过服务端 TTL：`离线`
- detect 失败或 detect 超时且没有其它有效可达信号：`离线`
- heartbeat、detect ACK、control ACK、info ACK、config push ACK、generic ACK 或非 `offline` 的 event 任意一个在 TTL 内：`在线`
- heartbeat 或 detect 上报 `wg_online=true`：当前 profile 的 WG 状态为 `running`
- heartbeat 或 detect 上报 `client_online=true, wg_online=false`：当前 profile 的 WG 状态为 `stopped`
- 静态节点、未初始化、离线、掉线、探测超时：WG 状态为 `unknown`

服务端当前在线 TTL 为 90 分钟。客户端 heartbeat 继续保持 30 分钟一次，以减少低价值空闲流量；其它真实通信 ACK 会同时刷新在线态。

### 探测回执建议字段

每次 `detect ack` 至少包含：

- `config_id`
- `node_id`
- `boot_id`
- `session_id`
- `client_online`
- `wg_online`

`heartbeat` 每 30 分钟上报一次，payload 与 `detect ack` 一致，只保留：

- `client_online`
- `wg_online`
- `mqtt_state`
- `wireguard_state`
- `last_error`
- `reported_at`

### ACK 设计

配置下发和控制命令都必须有 ACK。

约束：

- 服务端向客户端下发配置，不以“已发布到 broker”视为成功
- 服务端向客户端下发控制命令，不以“已发布到 broker”视为成功
- 只有客户端返回对应 ACK，且 ACK 状态为成功，才算这次动作真正完成

也就是说，以下两类消息都必须一来一回闭环：

- 配置下发
- 控制命令

控制命令 ACK 至少三态：

- `accepted`
- `applied`
- `failed`

必要时再加：

- `skipped`
- `superseded`

同一 profile 内的控制命令必须串行执行，避免：

- 配置下发和 stop/restart 并发
- 多次 sync 覆盖顺序混乱

这里的 `stop/restart` 指服务端下发给客户端的 WireGuard 控制动作，不是本地 `wfmctl` profile 级命令。本地不提供 profile 级命令入口。

### 不需要 ACK 的消息

以下消息不做 ACK：

- 客户端 `heartbeat`
- 客户端 `event`

这两类消息属于客户端到服务端的单向推送：

- 客户端发出后即可视为完成
- 服务端负责存储、展示和超时清理
- 不再反向回一个“收到状态”或“收到日志”的 ACK

## 最小服务端 API

为了让 `wfm-agent` 能独立完成工作，服务端至少要补这几类客户端专用接口。

注意：绑定接口使用客户端专用临时 token，不复用后台管理员 token。

### 1. 绑定

#### `POST /api/client/v1/bind`

用途：

- 用 5 分钟临时 token 完成客户端绑定

请求：

- `token`
- `hostname`
- `platform`
- `client_version`

响应：

- `profile`
- `mqtt`
- `topics`
- `desired_conf`

说明：

- 这是运行期唯一允许使用的 HTTP 初始化接口
- 绑定成功后，客户端不再依赖 HTTP 参与业务主链
- 服务端在绑定时负责生成或轮换节点专属 MQTT 凭据，并同步到 EMQX
- 服务端在绑定成功后把该节点标记为“客户端已初始化”，控制台端点页面才从初始化页切换到真正控制页

### 1.1 绑定命令生成

控制台动态节点需要一个独立接口或能力，用于生成“一次性节点绑定命令”。

要求：

- 只针对动态节点开放
- 默认有效期 5 分钟
- 只能成功使用一次
- 成功 bind 后立即失效
- 动态节点改成静态节点后，之前未使用的命令也必须失效
- 重置客户端后，可以重新生成新的绑定命令

### 2. EMQX 授权回查

#### `POST /api/internal/emqx/authz`

用途：

- 供 EMQX 在客户端 publish / subscribe 时回查授权结果

请求核心字段：

- `username`
- `clientid`
- `topic`
- `action`

响应语义：

- `allow`
- `deny`

说明：

- `wfm` 不再把 ACL 静态复制到多处，而是始终以当前节点业务状态为真相源
- 节点停用、删除、配置停用后，授权结果必须即时反映

## 当前结论

客户端应该按“无界面后台系统组件”来设计，而不是按“桌面应用”来设计。

`wfm-agent` 是唯一核心，`wfmctl` 是唯一主交互入口。  
绑定只走一次 HTTPS 临时 token，后续业务通信全部走 MQTT。  
本地命令只维护系统服务，不提供 profile 级控制；具体控制动作全部由服务端通过 MQTT 下发。  
托盘未来可以加，但永远只是附加项，不是主路径。

WG 运行态约束：

- `start` / `stop` / `detect` / `heartbeat` 只针对当前 profile 的 `interface_name`。
- `config/push` 必须针对当前 profile 立即生效：如果当前接口正在运行，先停止当前接口，再写入新配置，最后重新启动；如果当前接口未运行，只写入配置。
- `wg_show` 是控制台诊断动作名；客户端实际执行裸 `wg` 还是 `awg` 由服务端下发的 `tunnel_protocol` 决定。
- 静态节点没有客户端运行态，服务端和前端必须始终显示 WG 状态为“未知”。
- 动态节点离线、掉线、未初始化时，WG 状态同样为“未知”。
